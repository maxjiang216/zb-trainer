# ZBLL Trainer Web App — Build Notes (2026-05-28)

A static web app for practicing ZBLL: pick cases, drill the algs, and choose
which alg to use per case (with attribution to the top cubers who use it). Built
on top of the existing Rust cube simulator in this repo.

Live stack: **Vite + React + TypeScript**, deployable to Vercel (`web/`).

## What we built

- **Cube engine in TypeScript** (`src/cube/`): a faithful port of the verified
  Rust reference (`../src/moves.rs`, `cube.rs`, `parse.rs`, `normalize.rs`) so
  algs can be applied and cases classified live in the browser.
  - `moves.ts` — move tables (copied verbatim from the corrected Rust tables),
    `then`/`inverse`, the `MoveSet`, and the 24 `cubeRotations`.
  - `cube.ts` — `CubeState`, `apply`/`applyAlg`, `f2lSolved`,
    `llEdgesOriented`.
  - `parse.ts` — the rotation-remapping parser (rotations re-frame later moves
    rather than permuting pieces; wide/slice expand to face + rotation).
  - `classify.ts` — `zbllCanonical` (rotation- + AUF-normalized fingerprint).
  - `facelets.ts` — derives visible sticker colors from a `CubeState`.
  - `trainer.ts` — the practice-loop logic.
- **Data pipeline** (`scripts/build-cases.ts`, `npm run gen:cases`): classifies
  the scraped `reco_zbll_canonical.json` algs onto the 472 known speedcubedb
  cases and emits `src/data/cases.json` — each case with its render state plus
  every alg annotated by source (speedcubedb / reco.nz) and the cubers who use
  it. **This file is committed** because the pipeline reads data from
  `../../reco_scraper/` (outside this repo), so it can't be regenerated on
  Vercel.
- **SVG case diagrams** (`components/CaseDiagram.tsx`): top-down speedcubedb-
  style recognition view (U-face 3×3 + side stickers, front at the bottom).
- **Three pages** (`pages/`): Cases (selection, grouped by OCLL subset),
  Train (the loop), Algs + per-case alg chooser with source/attribution.
- Selection and per-case alg choices persist in `localStorage` (`store.ts`).

## The practice loop (the part we iterated on most)

The mechanic, after two rounds of correction from the original spec:

- The virtual cube `V` starts solved (Reset → solved).
- Each round names a case and you **apply its alg forward** to `V`. The result
  becomes the next round's `V`, so practice chains continuously:
  `V₀ = solved`, `Vₙ = applyAlg(Vₙ₋₁, algₙ)`. Applying an alg to a solved cube
  lands you in that alg's *inverse case*; because every ZBLL alg preserves F2L
  and edge orientation, the cube stays a recognizable last-layer state the whole
  time — **no scrambling needed**.
- The trainer also shows **the case the alg solves** — the recognition image —
  which is always `invert(alg)` applied to a solved cube.
- No post-AUF is applied; AUF variety arises naturally as the chain progresses.

This is the *reverse* of normal solving: you drill alg execution, and the
before/after panels verify each alg landed your cube where it should.

## Issues we ran into

1. **Wrong loop direction (the big one).** The first implementation presented
   each case as the *exact inverse* of its alg, so `alg ∘ invert(alg)` always
   returned to solved — the "resulting" panel was mathematically forced to be a
   solved cube and carried zero information. Verified the problem analytically:
   across all 1,093 (case, alg) pairs a correct solve leaves **zero** leftover
   rotation, so there is no "skipped post-AUF" state to show. The fix was to
   apply algs **forward** and chain — the cube starts solved, you apply the alg,
   you get the inverse case (per the user's model).

2. **Net rotations break the U-up assumption.** Algs containing rotations or
   wide moves (e.g. `y … r …`) leave the cube in a net-rotated frame, so after
   applying one forward, F2L is no longer on the bottom and the diagram would
   render sideways (~⅓ of cases). On a real cube you just re-grip; the model now
   re-orients each result to the unique cube rotation that lands F2L solved
   (`reorientToTop`).

3. **TS port had to be proven, not trusted.** Before relying on the ported
   classifier we confirmed it reproduces the Rust reference *exactly*: rotation
   group = 24, the same 7 known-bad cases fail to classify
   (`H6, H18, H19, H29, H40, T46, L23` — bad alg strings in `known_zbll.json`),
   and the same 343/465 reco coverage. The facelet color derivation was
   validated against a hand-computed `R` move before building the renderer.

4. **Build tooling.** `tsc -b` type-checked the Node build script's `node:`
   imports against the DOM-only app config. Split into `tsconfig.json` (app,
   `src` only) + `tsconfig.node.json` (scripts), added `@types/node`, and
   dropped `vite.config.ts` from the Node check (it pulls `WebWorker` lib types).

## Known gaps / future work

- **465 of 472 cases.** The 7 cases above are missing because their reference
  alg strings in `known_zbll.json` are malformed (same bad data the Rust
  `NOTES.md` documents). Fix = correct those 7 strings, then re-run
  `npm run gen:cases`.
- **CI does not gate the web app** — the repo workflow has `javascript: false`.
  Flip it on if we want type/lint checks enforced in CI.
- Only ZBLL for now (ZBLS data exists but is out of scope here).
- Possible niceties: timer/stats, smarter case sequencing (cover the selected
  set rather than pure random), forced pre-AUF variety, mirror/inverse drills.

## Commands

```bash
cd web
npm install
npm run gen:cases   # regenerate src/data/cases.json (needs ../../reco_scraper)
npm run dev         # local dev server
npm run build       # type-check + production build (dist/)
npm run lint        # tsc --noEmit on app + scripts
```
